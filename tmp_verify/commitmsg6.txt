优化: 降低每轮 AI 调用数（阶段六）

先用插桩 fetch 实测了单轮出站请求数，而不是读代码猜。实测结果
（5 个在场角色）：8 次请求 = 5 次角色推演 + 1 路由 + 1 正文 + 1 抛光，
对照组单角色 = 2 次。

改动：

1. 角色推演 N 次 → 1 次（characterSimulator.simulateCharactersBatch）
   原实现是 Promise.all(每角色一次请求)，首字延迟 = max(N 个推演)。
   实测 1/3/5/8 角色分别发 1/3/5/8 次请求，改后恒为 1 次。
   顺带改善一致性：原先各角色互相不知道对方在想什么，一次调用里
   模型能统筹（谁在回避、谁在逼近）。
   每个角色的档案与情报差仍按角色隔离注入（inactive 不带对话内容），
   只是把 N 个 prompt 拼进一个请求。
   保底：数组解析失败时退回逐角色请求，不丢整轮推演；模型漏输出
   某角色时补空动作，保持与输入等长；编造的角色名被丢弃。
   单角色时仍走原聚焦 prompt（更省 token，且无批量格式开销）。

2. 抛光不再阻塞正文（stage7_post）
   原实现 await polishText：用户流式读完整段正文后，还要空等一次
   完整调用的时间才能看到"发送完成"。改为同步返回正文 + 后台
   polish Promise，调用方先渲染、抛光完成后按引用定位那条消息原地替换。
   若期间用户又发了一轮或做了重生成，定位失败就丢弃结果。

3. 修一个被抛光掩盖的 bug：原实现先 await polishText，随后又用
   `displayText = raw.replace(META…)` 把它整段覆盖 —— 只要 AI 输出了
   ___META___，这次抛光就白花了一次 API 调用。改为先剥离 META 再抛光。

4. 修 META 损坏时的泄漏：原正则只匹配合法 JSON，坏掉的 ___META___{...
   会原样出现在用户可见正文里。改为先按标记位置整段砍掉，再尝试解析。

顺带清理：WorldChatScreen 不再订阅 activeChars/attitudes/summary
（服务层直接读 store，订阅只带来无谓重渲染）；删除死函数 normalizeSession
与 stage4 的遗留导入。

新增测试 23 个：
- batchSimulation.test.ts（12）：请求数 1 vs N、情报差隔离、损坏回退、
  漏角色补齐、互动标记解析与未知角色过滤、maxTokens 随角色数增长
- stage7Post.test.ts（11）：META 剥离、抛光与 META 不互相干扰、
  非阻塞语义、失败回落、新角色解析

验证：tsc 0 错误；jest 12 套件 98 用例通过；expo export 成功（664 modules）。

注意：本轮只做了请求数下降，**没有**合并 router 与 simulation。
两者 prompt 形态差异大（结构化路由决策 vs 逐角色第一人称推演），
合并省 1 次请求但可能损伤推演质量，收益不划算。首字延迟的构成因此是
「1 次推演 + 1 次路由（并行）」而非「1 次」，仍有优化空间但需实测验证。
